# Домашнее задание №2. Модуль «ПОС» (Преподавательская Оценка Студентов)

## 1. Архитектура решения (Hexagonal Architecture / Ports & Adapters)

Проект реализован с использованием **Hexagonal Architecture (Ports and Adapters)**.
Главный принцип — **зависимости направлены строго внутрь**. Ядро приложения (домен) ничего не знает о базе данных, консоли или фреймворке Spring. Связь с внешним миром осуществляется через интерфейсы (порты), реализации которых (адаптеры) находятся на периферии.

**Карта слоев и направление зависимостей:**
`Infrastructure (Adapters) --> Application (Use Cases) --> Domain (Core)`

*   **`domain/` (Ядро)** — Содержит сущности (Entity), объекты-значения (Value Object), доменные сервисы (Domain Service) и интерфейсы репозиториев (Ports). Полностью изолирован от внешних технологий.
*   **`application/` (Сценарии)** — Оркестрирует работу домена. Содержит классы сценариев (`PosManagementService`), которые вызывают методы домена и сохраняют результаты через порты.
*   **`infrastructure/` (Адаптеры)** — Реализует порты для взаимодействия с внешним миром. Включает `InMemory-репозитории` (адаптеры хранения) и `ConsoleUI` (адаптер пользовательского интерфейса).
*   **`config/` (Composition Root)** — Единственное место, где используется Spring DI для сборки объектного графа и связывания портов с конкретными адаптерами.

## 2. Карта DDD (Ubiquitous Language)

Модель спроектирована в соответствии с принципами Domain-Driven Design (DDD):

*   **Entity (Сущности)** — объекты, обладающие уникальной идентичностью (ID):
    *   `Student` — студент.
    *   `Criterion` — критерий оценивания (имеет название, максимальный балл и вес).
    *   `Evaluation` — факт выставления оценки (связывает студента, критерий и балл).
*   **Value Object (Объект-значение)** — объект, не имеющий идентичности, определяемый только своими атрибутами:
    *   `Score` — балл. Инкапсулирует инвариант (балл не может быть отрицательным).
    *   *Пример Entity vs VO:* Два студента с именем «Иван» — это две разные Entity (у них разные ID). Две оценки «8.5» — это два одинаковых VO (если их значение равно, они идентичны).
*   **Domain Service (Доменный сервис)**:
    *   `GradeCalculator` — содержит логику расчета итогового балла. Правило не принадлежит ни `Student`, ни `Criterion`, поэтому вынесено в отдельный сервис.
*   **Repository (Порт)**:
    *   Интерфейсы `StudentRepository`, `CriterionRepository`, `EvaluationRepository` описывают контракт сохранения данных, не завися от способа реализации (в памяти, в БД и т.д.).

**Защищаемые инварианты:**
1.  `Score` не может быть отрицательным.
2.  `Evaluation` не может быть создана с баллом, превышающим `maxScore` критерия (защищено фабрикой `EvaluationFactory`).
3.  Оценку можно выставить только по существующему критерию из рубрикатора (проверяется в `PosManagementService`).

## 3. Обоснование паттернов GoF

В проекте применено ровно по одному паттерну из каждой группы, чтобы они решали конкретные проблемы домена, а не существовали «для галочки»:

1.  **Creational (Порождающий) — Factory Method (`EvaluationFactory`)**:
    *   **Где:** `domain/factory/EvaluationFactory.java`
    *   **Боль:** Необходимо гарантировать, что при создании оценки балл не превышает максимально допустимый. Фабрика централизует создание `Evaluation` и проверяет инвариант `score <= criterion.maxScore()`.
2.  **Structural (Структурный) — Facade (`PosFacade`)**:
    *   **Где:** `application/PosFacade.java`
    *   **Боль:** Консольному интерфейсу не нужно знать, как собирать данные для отчета (какие репозитории дергать, как считать итог). Фасад скрывает эту сложность, предоставляя UI простые методы (`registerStudent`, `getStudentResult`).
3.  **Behavioral (Поведенческий) — Strategy (`GradeCalculator`)**:
    *   **Где:** `domain/service/WeightedGradeCalculator.java`
    *   **Боль:** Правила подсчета итогового балла могут меняться (например, заказчик захочет считать сумму баллов, а не средневзвешенное). Интерфейс `GradeCalculator` позволяет подменять алгоритм без изменения класса `PosManagementService`.

## 4. Роль ИИ

ИИ использовался как ассистент-черновик: с ним обсуждалась структура пакетов, генерировались заготовки интерфейсов, стандартный boilerplate-код и подсказки по API (Spring, JUnit, Gradle). Готовая финальная архитектура, работающая бизнес-логика, тесты и конфигурация собраны вручную — ИИ выдавал заготовки, которые приходилось переписывать под требования ТЗ и семинаров.

**Что именно делал ИИ (черновики, которые потом перерабатывались):**

- **Структура пакетов (черновик).** Изначально ИИ предлагал простую структуру `model`, `service`, `ui`. Итоговая структура — `domain/`, `application/`, `infrastructure/`, `config/` — спроектирована мной на основе лекций по Hexagonal Architecture (Ports & Adapters).
- **Заготовки интерфейсов (черновик).** `StudentRepository`, `CriterionRepository`, `EvaluationRepository` были сгенерированы ИИ, но доработаны мной для строгого соответствия паттерну Repository (Port) и добавления нужных методов вроде `findByStudentId`.
- **Заготовки DTO / Value Objects (черновик).** ИИ написал базовые `record` (например, `Student`, `Criterion`). Валидация (инварианты) и бизнес-правила в конструкторах добавлены мной.
- **Подсказки по API Spring / JUnit.** ИИ подсказывал, как использовать `@SpringBootTest`, `@Configuration(proxyBeanMethods = false)` и настраивать `build.gradle.kts` (Checkstyle, JaCoCo). Финальный вид конфигурации — результат моей ручной доработки под структуру практик.
- **Часть Javadoc.** ИИ писал черновики Javadoc для публичных методов. Формулировки переписаны мной, чтобы соответствовать Checkstyle Sun.
- **Черновики тестов (часть).** ИИ подготовил первые версии тестов. Граничные случаи (например, проверка на отрицательный балл или превышение максимума) добавлены вручную.
- **Черновик `ConsoleUI`.** Базовый скелет меню был от ИИ, но обработка ошибок ввода (`try-catch` на `NumberFormatException`), цикл работы и вывод данных переписаны мной.

**Что сделано мной самостоятельно:**

- **Архитектура**: спроектировал слои так, чтобы зависимости строго шли внутрь (`Infrastructure -> Application -> Domain`). Настроил Composition Root через Spring `@Bean`.
- **DDD и инварианты**: выделил Entity (`Student`, `Criterion`, `Evaluation`) и Value Object (`Score`). Реализовал защиту инвариантов: запрет на отрицательный балл (в `Score`) и запрет на превышение максимума критерия (в `EvaluationFactory`).

Для работы требуется JDK 25.

**Полная сборка (тесты, Checkstyle, проверка покрытия JaCoCo):**

```bash
./gradlew :modules:homework-2:clean :modules:homework-2:build
```
